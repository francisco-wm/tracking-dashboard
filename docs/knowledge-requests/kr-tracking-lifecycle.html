Knowledge request tracking

Every event we send to PostHog across a knowledge request’s life, from the moment the AI spots a gap to the moment the requester closes it. Three events are new, four need a small change, and five are already in place.

Already in place Needs a change New event
  1. 1

    Gap detected

    The AI notices missing knowledge in a chat and drafts a request. Nothing is sent to anyone yet.

    knowledge_gap_detectedChange

    Fires when the chat agent flags a gap and the draft request is created.

    Where
    Backend: chat-agent.service.ts, getting-started-agent.service.ts
    Has
    conversation_uuid, message_id

    To do: add knowledge_request_uuid, so a gap can be linked to the request that follows.

  2. 2

    Request sent

    The requester picks people or teams and clicks Request.

    knowledge_request_createdChange

    Fires once, when the requester sends the request with its first assignees.

    Where
    Backend: posthog.listener.ts
    Has
    knowledge_request_uuid, user_id

    To do: add assigned_to: users, teams or both. Add source: where the request started, so new ways of creating requests can be compared later.

  3. 3

    Routing

    The request reaches assignees. They open it, ignore it, or reject it, and the requester can change who’s assigned.

    knowledge_request_openedIn place

    Fires the first time any assignee opens the request.

    Where
    Backend
    Has
    knowledge_request_uuid, assignee_id, time_since_assigned_seconds
    knowledge_request_ignoredIn place

    Fires 7 days after sending if no assignee has opened it.

    Where
    Backend
    Has
    knowledge_request_uuid, assignee_id, assignee_team_ids
    knowledge_request_assignedChange

    Should fire when the requester changes assignees after the request was sent.

    Where
    Backend: posthog.listener.ts
    Has
    knowledge_request_uuid, assignee_id, assignee_team_ids

    To do: stop firing it together with created. Fire it only on later assignee edits by the requester.

    knowledge_request_rejectedNew

    Fires when a direct assignee rejects the request.

    Where
    Backend: reject endpoint
    Sends
    knowledge_request_uuid, reason, reassigned (true / false)
    knowledge_request_reassignedChange

    Only when a rejection includes someone to pass it to

    Fires when the rejecting assignee picks someone else.

    Where
    Frontend: reject modal
    Has
    knowledge_request_uuid, user_uuid, assigned_user_uuid

    To do: move it from the old direct-reassign action into the reject flow.

  4. 4

    Answers

    The AI may suggest an existing answer, and people publish their own. A request can collect several answers.

    system_contribution_created
    system_contribution_approved
    system_contribution_rejected    In place

    Fire when the AI suggests an answer, and when the requester accepts or rejects it.

    Where
    Backend: system-contribution.service.ts
    Has
    knowledge_request_id, knowledge_fragment_id
    knowledge_request_answeredNew

    Fires each time someone publishes an answer to the request.

    Where
    Backend: when the reply is published
    Sends
    knowledge_request_uuid, reply_number, answerer_role, seconds_open (time since the request was sent)
  5. 5

    Closed

    The requester decides the request is done, or no longer needed.

    knowledge_request_closedNew

    Fires when the requester resolves or cancels the request.

    Where
    Backend: resolve and cancel endpoints
    Sends
    knowledge_request_uuid, outcome, reply_count, seconds_open (time since the request was sent)

For the devs

Backend

  • Add knowledge_request_rejected, knowledge_request_answered and knowledge_request_closed to the allowed event names in posthog.service.ts.
  • Map them in posthog.listener.ts, next to created, opened and ignored.
  • Every new event carries knowledge_request_uuid.

Frontend

  • Move knowledge_request_reassigned into the reject modal, firing only when a reassignment target is chosen.
  • If someone can be reassigned to a team, add assigned_team_uuid.

Property values

Property Value Meaning
reason unclear_question Need more information / question not clear
dont_know I don’t know the answer
duplicate Duplicate request
already_available Content already available
none No reason chosen
answerer_role direct_assignee Assigned by name
team_member Reached through an assigned team
requester Answered their own request
assigned_to users Only people assigned
teams Only teams assigned
both People and teams
source chat Gap detected in the main chat
getting_started_chat Gap detected in the Getting Started chat
outcome resolved Requester resolved it
cancelled Requester cancelled it

Left out on purpose

  • A generic status-change event. closed covers the transitions that matter, and the first answer implies In progress.
  • Tracking the cross-team warning and the lost-access draft. Both are edge cases; add them if they turn out to happen often.
